# 1. Verify IL Jobs from Bastion Server

## Objective

Verify whether IL jobs are running successfully in the Kubernetes cluster and identify any failed or incomplete jobs.

### Login to Bastion Server

```bash
sudo su ec2-user
```

### Configure Kubernetes Access

```bash
aws eks update-kubeconfig --region eu-west-2 --name ebs-prd-cluster
```

### List All Jobs in Production Namespace

```bash
kubectl get jobs -n ebs-prd
```

### Sample Output

```text
NAME                                   COMPLETIONS   DURATION   AGE
il-core-account-rebuild-job-deployment 1/1           2m         5h
```

### Understanding the Output

* **COMPLETIONS = 1/1**
  * Job completed successfully.

* **STATUS = Complete**
  * Job execution completed without errors.

* **AGE**
  * Displays when the job was created.

### Job Health Indicators

#### Successful Job

```text
1/1 Complete
```

#### Failed or Incomplete Job

```text
0/1
```

or

```text
Failed
```

These jobs require further investigation.

***

# 2. Re-Run a Failed Job

## Objective

Create a new execution of an existing job when a previous job has failed.

### Command

```bash
kubectl create job --from=job/<job-name> <new-job-name> -n ebs-prd
```

### Example

```bash
kubectl create job --from=job/il-core-account-rebuild-job-deployment il-core-account-rebuild-job-rerun -n ebs-prd
```

### Expected Result

A new Kubernetes job is created and starts execution.

***

# 3. Manually Trigger Deposit Transaction Import Job

## Objective

Execute the Deposit Transaction Import job manually from the existing CronJob configuration.

### Command

```bash
kubectl create job --from=cronjob/mtl-deposit-transaction-import-job-deployment mtl-deposit-transaction-import-job-deployment-$(date +%s) -n ebs-prd
```

### Explanation

* Creates a one-time job from an existing CronJob.
* Uses the current timestamp to generate a unique job name.
* Executes the job in the `ebs-prd` namespace.

### Verify Job Creation

```bash
kubectl get jobs -n ebs-prd
```

### Expected Result

The newly created job should appear in the list and progress toward completion.

# 4. Navigate to CloudWatch Logs Insights

## Objective

Use CloudWatch Logs Insights to investigate application logs, transaction failures, and job execution details.

### Steps

1. Login to AWS Console.
2. Navigate to:

```text
CloudWatch → Logs Insights
```

3. Open the query editor.

***

# 5. Select the Appropriate Log Group

## Log Group

```text
/aws/eks/ebs-prd-cluster/application
```

### Purpose

This log group contains application logs generated by services running in the EKS cluster.

### Steps

1. Click **Log Group Name**.
2. Select:

```text
/aws/eks/ebs-prd-cluster/application
```

***

# 6. Configure Time Range

## Importance

Selecting the correct time range is critical. Incorrect time selections may result in no logs being displayed.

### Steps

1. Select **Time Range**.
2. Choose **Relative**.
3. Select:

```text
1 Hour
```

or

```text
5 Hours
```

4. Click **Apply**.

### Recommendation

Start with a wider range if logs cannot be found.

***

# 7. Run a Basic Log Query

## Query

```sql
fields @timestamp, @message
| sort @timestamp desc
| limit 1000
```

### Purpose

Displays the most recent application logs.

### Expected Output

* Timestamp
* Log Message

This query should always be the starting point of any investigation.

***

# 8. Filter Logs for Specific Jobs or Transactions

## Deposit Transaction Search

```sql
fields k8s_labels.deployment, log
| filter @message like 'deposit-transaction'
| sort @timestamp desc
| limit 10000
```

### Uses

Filter logs using:

* Transaction ID
* Job Name
* Error Message
* Correlation ID
* Exception Keywords

Example:

```text
ERROR
Exception
deposit-transaction
```

***

# 9. Troubleshooting "No Results Found"

## Possible Causes

### Incorrect Time Range

Logs may exist outside the selected time range.

### Wrong Log Group

Verify the correct log group is selected.

### Incorrect Filter

The search keyword may not exist in the logs.

### Logs Not Generated

The application may not have produced logs during the selected period.

***

## Resolution Steps

### Increase Time Range

Try:

```text
5 Hours
12 Hours
24 Hours
```

### Remove Filters

Run the basic query without filters.

### Verify Log Group

Ensure the selected log group is:

```text
/aws/eks/ebs-prd-cluster/application
```

***

# 10. Correlate with Application Logs

## Objective

Match CloudWatch log events with application errors.

### Common Errors

```text
Transaction file download error
```

```text
IllegalArgumentException
```

### Investigation Process

1. Identify the error timestamp.
2. Locate surrounding log entries.
3. Follow the transaction flow.
4. Identify the point of failure.
5. Capture relevant exception details.

***

# 11. Recommended Troubleshooting Workflow

### Step 1

Open CloudWatch Logs Insights.

### Step 2

Select the correct Log Group.

### Step 3

Set the appropriate time range.

### Step 4

Run the basic query:

```sql
fields @timestamp, @message
| sort @timestamp desc
```

### Step 5

Filter for errors:

```sql
fields @timestamp, @message
| filter @message like 'ERROR'
| sort @timestamp desc
```

### Step 6

Identify:

* Error Message
* Impacted Service
* Transaction ID
* Correlation ID
* Timestamp

### Step 7

Trace the complete request flow.

### Step 8

Determine whether the issue is:

* Application Related
* Data Related
* Infrastructure Related

***

# 12. Key Takeaways

* Always verify the selected log group before running queries.
* Always check the time range if no logs are returned.
* Start investigations with a basic query before applying filters.
* Use transaction IDs and correlation IDs for deep analysis.
* Verify Kubernetes job status before investigating application logs.
* Failed jobs should be re-run only after understanding the root cause.
